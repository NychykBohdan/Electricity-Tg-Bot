### Хто атакує
- **Будь-який користувач Telegram.** Бот публічний, ролей немає. Може використати модифікований клієнт або userbot, щоб надіслати довільний `callback_data` і текст.
- **Анонім з інтернету.** Бачить `POST /telegram`, `GET|POST /cron`, `GET /`.
- **Скомпрометоване або несправне upstream-API** `be-svitlo.oe.if.ua`. Ризик низький.

## 2. Знахідки

| ID | Серйозність | Коротко |
|---|---|---|
| F1 | **High** | Необмежена кількість підписок дає змогу одному користувачу заблокувати сповіщення й нагадування для всіх |
| F2 | **Medium** | Немає rate limit, тому бот працює як проксі до `be-svitlo.oe.if.ua` (пошук за рахунком) |
| F3 | Low | `cb_group` зберігає чергу з `callback_data` без whitelist і вставляє її в HTML без екранування |
| F4 | Low | `msg_account` не валідує номер рахунку. Чергу з відповіді API не перевірено й не екрановано |
| F5 | Low | Текст `CollectorError` іде в HTML-алерт адміну без екранування, і алерт може загубитись |

### F1 — Один користувач може «задушити» розсилку для всіх (High)

**Де:**
- `app/bot/handlers/onboarding.py:186-200` (`finish`): нова підписка створюється без жодного ліміту на користувача;
- `app/db/repo.py:215-220` (`add_subscription`): ліміту теж немає;
- `app/services/poller.py:66-74` (`notify`): надсилає послідовно кожній підписці групи;
- `app/services/notifier.py:31-41` (`send`): один глобальний `asyncio.Lock`, а при `TelegramRetryAfter` чекає `retry_after + 1` с, до 3 спроб;
- `app/services/poller.py:51` (`poll_source` → `save_snapshot`): знімок зберігається **до** розсилки;
- `app/services/reminders.py:36-62`: ті самі послідовні відправки по всіх підписках.

**Сценарій атаки:**
1. Атакувальник скриптом через userbot проходить «➕ Додати адресу → Я знаю свою чергу → `g:3.2` → `tt:0`» сотні разів. Кожен прохід створює нову підписку на ту саму популярну чергу. Перевірок на дублікати чи кількість у коді немає (`grep` по `limit|throttl|middleware` нічого не знаходить).
2. Коли графік черги `3.2` змінюється, `Poller.notify` надсилає кожній підписці окреме повідомлення. Сотні з них йдуть в **один чат атакувальника**.
3. Telegram обмежує відправку в один чат приблизно 1 повідомленням на секунду і повертає `RetryAfter`. `Notifier.send` тримає глобальний лок і спить `retry_after + 1` с на кожну спробу, тому вся розсилка стоїть.
4. На Vercel `/cron` впирається в ліміт тривалості функції (`maxDuration` у `vercel.json` не задано) і обривається. Знімок уже збережено (`poller.py:51`), тож на наступному тіку зміни «немає». **Решта користувачів цієї черги і всіх черг, що обробляються після неї, сповіщення не отримають ніколи.** Нагадування (`reminders.py`) страждають так само: їхнє вікно минає, поки розсилка стоїть.

**Захист вище по стеку:** не знайдено. Webhook-секрет захищає лише від підробки апдейтів, а атакувальник діє як звичайний користувач.

**Рекомендація:**
- Обмежити кількість підписок на користувача (наприклад, 5) у `finish()` до `add_subscription`, а також заборонити дублікати `(user_id, source_key, group)`, наприклад через `UniqueConstraint`.
- У `notify`/`check_reminders` групувати відправки за `user_id`: один користувач отримує одне повідомлення на подію.
- Після `RetryAfter` для конкретного чату пропускати цей чат, а не тримати глобальний лок. Розглянути позначку «сповіщено» для кожної зміни, щоб обірвана розсилка продовжувалась на наступному тіку.

### F2 — Немає rate limit: бот як проксі для API обленерго (Medium)

**Де:**
- `app/bot/handlers/onboarding.py:136-140` (`msg_account`): кожне текстове повідомлення в стані `AddSub.account` дає `POST` на `https://be-svitlo.oe.if.ua/schedule-by-search`;
- `app/runtime.py:41-43`: `Dispatcher` без жодного middleware обмеження частоти;
- `app/web.py:44`: кожен апдейт викликає `runtime()`, тобто новий engine БД і нове з'єднання.

**Сценарій атаки:** атакувальник один раз переходить у стан `AddSub.account` (кнопка «🧾 Знайти за особовим рахунком»). Якщо черга знайдена, стан переходить у `title`, і атакувальник повертається тим самим шляхом. Якщо ні, бот перекидає його в `AddSub.group`. Далі він шле перебір номерів рахунків:
- кожне повідомлення стає запитом до `be-svitlo.oe.if.ua` з IP бота. Обленерго може заблокувати цей IP, і тоді `Poller` (той самий IP/egress) перестане отримувати графіки **для всіх користувачів**;
- атакувальник отримує анонімний перебір «рахунок → черга» через чужу інфраструктуру;
- кожен апдейт коштує виклик функції Vercel і з'єднання з Supabase.

**Захист вище по стеку:** немає. Telegram обмежує лише частоту відправки повідомлень клієнтом, але цього недостатньо, щоб захистити upstream.

**Рекомендація:** додати outer-middleware з лімітом на `from_user.id`. Стан тримати в БД (`kv` або окрема таблиця), бо на Vercel пам'ять між запитами не живе. Для `msg_account` поставити окремий жорсткіший ліміт, наприклад 5 пошуків на годину на користувача.

### F3 — `cb_group`: черга з `callback_data` без whitelist (Low)

**Де:** `app/bot/handlers/onboarding.py:156-161`
```python
group = cb.data.split(":")[1]
await state.update_data(group=group)
await ask_title(cb.message, state, edit=True, intro=f"✅ Черга <b>{group}</b>")
```

**Сценарій:** модифікований клієнт у стані `AddSub.group` надсилає `g:<довільний рядок до ~60 байт>`.
- Рядок вставляється в HTML без `escape`. Розмітка йде лише в чат самого атакувальника, тому «self-injection» інших не зачіпає. Невалідний HTML дає `TelegramBadRequest`.
- Рядок зберігається в `subscriptions.group` (`String(8)`). На Postgres довге значення дає `DataError`, і підписка не створюється. На SQLite зберігається як є, але такій підписці ніколи не приходять дані.
- Далі `group` скрізь виводиться через `escape` (`sub_card`, `format_schedule`, `format_change`), тому стороннім користувачам це не шкодить.

**Чому Low:** вплив обмежено власними даними атакувальника. Це порушення цілісності даних, а не вразливість щодо інших. Проте це прямо суперечить правилу «кожне значення з `callback_data` — за whitelist».

**Рекомендація:** `if group not in GROUPS: return await cb.answer()`, а в `intro` використовувати `escape(group)`.

### F4 — `msg_account`: немає валідації рахунку і відповіді API (Low)

**Де:** `app/bot/handlers/onboarding.py:138-152`

**Що підтверджено кодом:**
1. `account = message.text.strip()` іде у зовнішнє API без перевірки формату й довжини (`:140`). URL-ін'єкції немає: значення передається в тілі форми, `aiohttp` його кодує. Проте довільний текст до 4096 символів таки йде upstream.
2. `address=f"Особовий рахунок №{account}"` (`:151`) може перевищити `String(200)` (`app/db/models.py:54`). На Postgres це дає `DataError` у `finish()`, і додавання адреси падає. SQLAlchemy за замовчуванням включає параметри запиту в текст винятку, тож введений текст потрапляє в `log.exception("Update handling failed")` (`app/web.py:49`). Реальний номер рахунку короткий, тому витоку справжніх даних цим шляхом немає.
3. Черга з відповіді API (`f"{queue}.{sub}"`, `app/collectors/prykarpattya.py:67`) не звіряється з `GROUPS` і вставляється в HTML без `escape` (`:152`). Щоб це використати, треба контролювати upstream-API.

**Рекомендація:** валідувати `^\d{5,20}$` (або реальний формат рахунку) до виклику API. Перевіряти `group in GROUPS` після `resolve_queue_by_account` і екранувати.

### F5 — Неекранований `CollectorError` в алерті адміну (Low)

**Де:** `app/services/poller.py:92`
```python
await self.notifier.send(self.admin_id, f"⚠️ Джерело {key} не відповідає вже {n} разів поспіль\n{e}")
```

**Сценарій:** текст `e` формується з `aiohttp`-винятку (`prykarpattya.py:77`), куди входить reason-phrase відповіді сервера. Якщо в ньому є `<` або `&`, Telegram відхилить HTML (`TelegramBadRequest`), а `Notifier.send` це лише залогує (`notifier.py:46-48`). Алерт надсилається **один раз**, при `n == ALERT_AFTER_FAILURES`, тож адмін не дізнається про збій джерела. Для цього потрібен контроль або дивна поведінка upstream, тому ризик низький.

**Рекомендація:** `escape(str(e))`. Краще взагалі не передавати сирий текст винятку: досить ключа джерела й лічильника.

## 3. Що потребує ручної перевірки (код не дає підтвердити)

- **N1. RLS у Supabase.** `Database.create_all()` (`app/db/repo.py:133`) і `_migrate()` (перестворення `sent_reminders`) створюють таблиці без `enable row level security`. Чи ввімкнено RLS у продакшн-базі, з коду не видно. Перевір у Supabase → Table Editor, що для `users`, `subscriptions`, `fsm_states`, `sent_reminders`, `schedule_snapshots`, `kv` RLS увімкнено. Інакше таблиці доступні через Data API (PostgREST) з anon-ключем.
- **N2. `?key=` для `/cron`.** Код приймає секрет і в query string (`app/web.py:54-56`), а такий URL осідає в логах Vercel і cron-сервісу. Перевір, що cron-job.org налаштовано на заголовок `Authorization: Bearer …`, і розглянь вимкнення `?key=`.
- **N3. Змінні оточення Vercel.** Переконайся, що секрети задано лише для Production, а не для Preview.

## 4. Що перевірено і не є проблемою

- Webhook і cron перевіряють секрет через `hmac.compare_digest` до будь-якої роботи. Якщо секрет не задано, відповідь 500.
- IDOR: усі хендлери з `sub_id` (`svp`, `sv`, `sub`, `st`, `ss`, `del`, `delok`) звіряють власника за `from_user.id`.
- `ss:` бере значення налаштування за індексом з whitelist, а не з `callback_data`. `update_user` приймає лише `PREF_FIELDS`.
- Користувацькі `title` і `address` екрануються у всіх місцях виводу (`menu.py`, `formatter.py`).
- SQL-ін'єкцій немає: міграції використовують лише константи.
- FSM-ключ включає `chat_id` і `user_id`, тож один користувач не може підмінити стан іншого.
- `.env` ніколи не потрапляв в історію git.
